# SD 热插拔恢复

用户已确认修复：拔卡后停止 SD 媒体操作、清理旧挂载；重新插卡后核对设备号并重新打开媒体资源；正确处理挂载和卸载失败。

现场证据：`/mnt/tf` 保留 `179:1` 的 FAT 挂载，而当前 `mmcblk0p1` 是 `179:9`。清理后只读挂载 `179:9`，目录重新可读。

## 恢复流程

1. 从 `/proc/self/mountinfo` 获取挂载设备号、文件系统和读写标志，与实际块设备节点核对，替代 `df` 输出解析。
2. 检测移除、设备号变化或挂载丢失时，先发布不可用状态，递增媒体代次。通过带序号的 UI 事件停止录制、音乐和相框，并让现有页面退出逻辑关闭数据库与文件。
3. SD 工作线程轮询事件确认，期间不持有 UI 会使用的锁。队列满时重试通知；卸载遇 `EBUSY` 时保留旧挂载并退避重试，不叠加新挂载。
4. 确认旧挂载消失、后台持久化操作结束后，挂载当前分区。只有设备号、FAT 类型、可写标志及容量检查通过才发布可用状态。
5. 在途抓拍绑定 SD 代次，写卡阶段持有短期 I/O 使用计数，避免旧请求落入新卡或未挂载的目录。拔卡清理保留网络实时预览。
6. 抓拍请求字段保留到完成回调；关闭预览只取消尚未交给编码线程的请求。线程成功启动后所有失败出口均通知一次完成，避免请求被覆盖或永久忙。
7. 显式格式化先打开并核对设备句柄，再将 `/proc/<应用PID>/fd/N` 传给原有格式化工具。句柄设置 close-on-exec，防止无关命令继承独占引用；结果经 UI 消费后才允许下一次请求。

## 边界

- 采用普通卸载，不自动格式化或修复文件系统，不调整驱动、时钟或音频算法。
- 保留已有 p1、p2、整卡 FAT 探测顺序。只读挂载不报告为可写。
- 格式化仍由既有显式操作触发，必须先完成资源释放和卸载；错误必须返回给 UI。
- 用户已有 ONVIF 日志注释，以及并行的 Wi-Fi/网络页面修改，不属于本次变更。
- 外部程序或终端持有 SD 文件/目录时，等待它释放占用；不强行关闭其他进程的资源。

## 验证

主机回归覆盖命令退出码、旧设备号残留、拔卡通知先于卸载、UI 确认、队列满重试、`EBUSY`、快速插回、挂载失败、只读/错误文件系统、在途 I/O 和代次失效。交叉编译相关模块，代码审查检查锁顺序与资源所有权。实机仍须验证实际卡槽、读写、格式化和媒体各场景。
